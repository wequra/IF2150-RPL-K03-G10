# BAB 1: Deskripsi Umum

## 1.1 Deskripsi Umum Sistem

Perangkat lunak kami dibuat agar dapat memantau dan mengelola air dan juga surya. 
Sistem ini dirancang dengan memfokuskan pada platform utama dan satu-satunya melalui website. Website dipilih dikarenakan dapat diakses oleh warga melalui device manapun. Beberapa fitur yang terdapat pada website antara lain adalah melihat ketersediaan air, status daya surya, tagihan iuran, analitik penggunaan komunal, pengelolaan iuran warga, dan platform laporan gangguan serta status perbaikan dari laporan yang masuk.

Dari kacamata pengguna, perangkat layar yang diusulkan ini berfungsi sebagai pusat kendali dan informasi yang memungkinkan operator fasilitas desa dan stakeholder untuk memantau status pompa air, tingkat keterisian tangki, serta juga daya panel surya dan baterai secara real-time. Selain itu, warga juga dapat mencari informasi yang mudah dipahami mengenai ketersediaan air, kondisi pasokan energi, rincian iuran, serta perkembangan laporan gangguan.

Alur kerja sistem ini yaitu menjadi jembatan antar dunia fisik dan digital dalam pengelolaan air dan energi komunal. Perangkat keras di lapangan seperti sensor pada tangki penampungan, pompa air, dan panel surya dapat mengirimkan data aktual ke platform web. Sistem kemudian memproses data tersebut menjadi informasi yang siap digunakan yaitu, tampilan ketersediaan air dan status daya pada dasbor warga, notifikasi peringatan pada teknisi ketika metrik daya sudah hampir habis, serta menyediakan data pemakaian bagi pengurus untuk keperluan analitik dan kalkulasi iuran.

Harapan dari penerapan solusi ini adalah terciptanya pengelolaan infrastruktur air dan energi komunal yang lebih terukur, transparan, dan berkelanjutan di tingkat komunitas. Dengan pemrosesan yang lebih terdigitalisasi, warga dapat memperoleh kepastian informasi tanpa harus bertanya langsung kepada pengurus, teknisi dapat melakukan menangani masalah di lapangan dengan lebih taktis, serta pengurus dapat mengelola data lebih cepat dalam mengambil keputusan komunitas dan kalkulasi iuran.

| ID KNF | ID Kebutuhan | Parameter | Deskripsi Kebutuhan |
| :--- | :--- | :--- | :--- |
| KNF01 | R09, R19, R25, R29, R32 | Security | Selama pengguna menggunakan sistem, sistem harus membatasi akses fitur sesuai peran pengguna dan menampilkan pesan penolakan apabila pengguna mencoba mengakses fitur yang tidak sesuai kewenangan. |
| KNF02 | R05, R08, R11, R21, R24 | Security | Ketika pengguna membuka data tagihan, laporan gangguan, atau catatan pemeliharaan, sistem harus menampilkan data sesuai kewenangan pengguna dan tidak menampilkan data milik pengguna lain. |
| KNF03 | R10, R13, R15 | Reliability | Bila koneksi jaringan terputus saat pengiriman data laporan atau data peringatan, maka sistem harus menyimpan data sementara dan mengirimkannya kembali setelah koneksi pulih tanpa menghilangkan data. |
| KNF04 | R17, R22 | Reliability | Ketika sistem menerima data riwayat kinerja perangkat atau catatan pemeliharaan, sistem harus menyimpan data tersebut dan menampilkannya kembali paling lama 5 detik setelah pengguna membuka halaman riwayat. |
| KNF05 | R13, R15 | Safety | Bila kapasitas baterai sudah melewati batas aman, maka sistem harus menampilkan peringatan kepada teknisi dan mengirim notifikasi kepada teknisi yang bertanggung jawab paling lama 3 detik setelah sistem menerima data kondisi kritis. |
| KNF06 | R01, R03, R24 | Availability | Selama jam operasional komunitas, sistem harus dapat diakses oleh warga, teknisi, dan pengurus dengan ketersediaan sistem minimal 99% per bulan. |
| KNF07 | R01, R03, R05, R08, R11 | Ergonomy | User Interface pada halaman pemantauan air, kelistrikan, dan pengisian form gangguan harus dibuat intuitif dengan menerapkan navigasi yang sederhana sehingga dapat digunakan oleh warga tanpa panduan pelatihan khusus. |
| KNF08 | R16, R18, R21 | Ergonomy | Teknisi akan sering melakukan aktivitas pemeliharaan fisik secara langsung di lapangan, sehingga User Interface pada fitur pencatatan log pemeliharaan dan pembaruan status laporan harus didesain agar mudah diakses dan dibaca melalui layar handphone yang kecil. |
| KNF09 | R01, R08, R18, R24 | Portability | Website harus bersifat responsif dan dapat dioperasikan dengan baik di berbagai web browser di berbagai perangkat (PC, handphone, tablet) tanpa mengharuskan pengguna untuk mengunduh aplikasi tambahan. |
| KNF10 | R31, R33, R45 | Portability | Hasil ekspor laporan iuran dan pemakaian bulanan harus dalam format berkas yang universal (PDF atau spreadsheet CSV) sehingga dokumen mudah untuk dipindahkan, dibuka, dan dicetak di mesin atau sistem operasi apa pun yang digunakan pengurus. |
| KNF11 | R01, R03, R34, R35 | Response time | Sistem harus dapat memperbarui data visualisasi dashboard paling lambat 2 detik setelah sistem menerima data terbaru dari sensor di infrastruktur sehingga informasi didapat secara real-time. |
| KNF12 | R24, R27, R44 | Response time | Saat pengurus mengakses dashboard analitik atau melakukan kalkulasi otomatis iuran warga, sistem harus dapat menyelesaikan perhitungan matematis dan merender grafik hasil dalam waktu paling lambat 5 detik agar tidak mengganggu pengalaman pengguna. |
| KNF13 | R34, R35, R39 | Memory | Firmware atau program pembacaan sensor pada unit mikrokontroler (ESP32 atau Arduino) harus dikompilasi secara efisien agar ukurannya tidak melebihi kapasitas memori internal (RAM) yang terbatas pada hardware tersebut. |


| Parameter | Penjelasan |
| :--- | :--- |
| *Availability* | Ketersediaan aplikasi, misalnya harus terus-menerus beroperasi 7 hari per minggu, 24 jam per hari tanpa gagal. |
| *Reliability* | Keandalan, misalnya tidak pernah boleh gagal (atau kegagalan yang ditolerir adalah …%) sehingga harus dipikirkan *fault tolerant architecture*. Biasanya hanya perlu untuk *critical application* yang jika gagal akan berakibat fatal. |
| *Ergonomy* | Kenyamanan pakai bagi pengguna. |
| *Portability* | Kemudahan untuk dibawa dan dioperasikan ke mesin/sistem operasi/*platform* yang lain. |
| *Memory* | Jika perhitungan kapasitas memori internal kritis (misalnya untuk P/L yang harus dijadikan *chips* dan ukurannya harus kecil). |
| *Response time* | Batasan waktu yang harus dipenuhi. Sangat penting untuk aplikasi *real time*. Contoh: "Aplikasi harus mampu menampilkan hasil dalam 4 detik", atau "ATM harus menarik kembali kartu yang tidak diambil dalam waktu 3 menit". |
| *Safety* | Yang menyangkut keselamatan manusia, misalnya untuk P/L yang dipakai pada sistem kontrol di pabrik. |
| *Security* | Aspek keamanan yang harus dipenuhi. |
